# S3 rules

Used for uploaded and produced files, versioned JSON Schema, and large workflow payloads (claim check).

## Layout
- One bucket per purpose and environment; do not mix schemas, documents and workflow payloads.
- Key pattern: `<domain>/<entity-id>/<yyyy>/<mm>/<uuid>-<safe-filename>` for documents; `schemas/<name>/<semver>/<name>.schema.json` for schemas; `payloads/<workflow-id>/<activity-id>.json` for claim-check payloads.
- No PII, user-supplied raw names, or secrets in keys. Sanitise filenames, never trust client paths.

## Safety
- Block Public Access on. Server-side encryption (SSE-KMS). TLS only.
- Access via least-privilege IAM per service (API: its prefixes only; worker: its prefixes only).
- Clients get presigned URLs with short expiry, exact key, method and content-type/size constraints. Never proxy unvalidated uploads into trusted prefixes; scan or validate before use.
- Schema bucket: versioning on, published schema objects are **immutable**. Never overwrite `.../1.2.0/...`; publish a new version. Consumers pin a version or read a `latest` pointer object.
- Payload bucket: lifecycle rule expires objects after the retention window.

## Code
- One thin storage client per repo; no `@aws-sdk` calls scattered through business code.
- Writes are idempotent (deterministic key, or conditional write) so activity retries are safe.
- Record `sha256`, `content-type`, `size` and source workflow/correlation ID as object metadata.
- Handle not-found, throttling and partial failures explicitly; classify retryable vs not.

## Testing
Use an S3-compatible container (for example LocalStack or MinIO) with path-style addressing. Test upload, duplicate upload, missing object, and expired presign.
